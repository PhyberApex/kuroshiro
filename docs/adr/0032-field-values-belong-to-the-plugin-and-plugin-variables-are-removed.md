# Field Values belong to the Plugin and reach every render; Plugin Variables are removed

Issue #1087, a decision ticket on the admin UI rebuild map (#1074), asked what a Plugin's field values and Plugin Variables are and whether the new UI saves them. Reading the code showed the question was larger than the UI. A Plugin's field definitions are real (imports create them from `custom_fields`, the Plugin API accepts them), but a stored value is written only by Configuration Import and read only by Configuration Export: the scheduler, the on-demand `/display` render and the Mashup renderer build their context from `trmnl`, `sensors` and Data Source data, so neither a stored value nor a field's default reaches a real render. Only the editor preview injects them. An imported Recipe that uses `{{ city }}` in its polling URL previews correctly and renders empty on the Device. Plugin Variables are further gone still: only Configuration Import and Plugin duplicate write them, and the resolver that would substitute them has no caller. Grilling settled the following.

- **A Field Value belongs to the Plugin, not to a Plugin Assignment.** The alternatives were a value per Assignment, or a Plugin value with a per-Device override, which is what the `PluginFieldValue.device` column and the archive's per-Assignment `fieldValues` were shaped for. Both mean a fetch and a render per Assignment where there is one per Plugin today, and neither has an answer for a Mashup slot, which points at a Plugin and has no Assignment. The protagonist runs one Device, and TRMNL also hangs values on the plugin instance. Showing one Plugin with different values on two Devices is done by duplicating the Plugin.
- **Saving Field Values is part of the UI rebuild, as a repair.** The rebuild admits nothing an admin cannot do today, and strictly an admin cannot save a value today. But the old editor shows the inputs and silently drops them, and Recipes with fields do not work without this. The API work is a build issue of its own; the new UI is specified around saved values.
- **Plugin Variables are removed outright.** Reviving them as per-Plugin secrets substituted into Data Sources was the alternative. Nothing creates them, Field Values cover the same need, and Data Source headers already hold credentials. The entity, the resolver (including its `${ENV_VAR}` substitution, equally unreachable) and the archive's `variables` go.
- **Values are addressable the way TRMNL addresses them.** `{{ trmnl.plugin_settings.custom_fields_values.<keyname> }}` and bare `{{ <keyname> }}`, in templates and in a Data Source's url, headers and body, in the preview and in every real render, so an imported Recipe works unmodified. A Data Source's data wins over a bare key of the same name. The value used is the Field Value, else the Plugin Field's default, else empty.
- **The admin can author Plugin Fields.** Add, edit, reorder and remove on the Plugin, where today only imports and the API can. An edit matches existing Plugin Fields by keyname so their values survive; today an update that carries `fields` deletes and recreates every row and the values cascade away. Removing a Plugin Field removes its value.
- **Six controls, and no import fails on a type.** Single-line text (also `url`), multi-line text, number, on/off, password, and select, which requires the importers to start keeping a field's options. `author_bio` is shown as a read-only credit. Any other type is single-line text.
- **A missing required value marks the Plugin and blocks nothing.** A required Plugin Field with neither a value nor a default puts the Plugin in a "needs values" state, visible on the Plugin and in the Plugins list; it still saves, can be assigned and renders. Blocking assignment would dead-end a fresh Recipe import and could pull a Plugin off a Device when a Recipe update adds a field.
- **A password-type Field Value is a secret.** Masked in the UI, write-only through the admin API (which reports only whether it is set), and replaced by the Redaction Sentinel in a Redacted Archive.
- **Field Values save with the Plugin, and saving re-renders at once.** The preview reflects unsaved edits; a save re-fetches and re-renders immediately rather than waiting out the refresh interval.
- **The archive `schemaVersion` goes up, and the previous version is still accepted.** Values move from the Assignment entry to the Plugin entry and `variables` disappears. Configuration Import refuses any other version today; it keeps accepting the previous one, ignoring its `variables` and per-Assignment `fieldValues` and warning in the import summary if either was non-empty. In practice they are empty in every archive the app has produced, since nothing in the running app could create them.

**Addendum (2026-10-05, issue #1259).** An on/off Field Value stays a string: whether `{% if show_wind %}` should work was asked separately, since a stored on/off value is the text `"true"`/`"false"` and every string is truthy in Liquid. TRMNL's own renderer hands Field Values to Liquid as strings too: its open-source preview server `trmnlp` stringifies every Field Value "to match production behavior" (`stringify_field_value`, `lib/trmnlp/config/project.rb`, usetrmnl/trmnlp@7848809). Kuroshiro already matches this, so no render change; a template compares `{% if show_wind == "true" %}` instead. One divergence worth keeping in mind: `trmnlp` passes a field's YAML `default` through unchanged when no value is set (`custom_field_defaults`, `lib/trmnlp/config/plugin.rb`), so on TRMNL an unset on/off field with a YAML boolean `default: true` can reach Liquid as a real boolean. Kuroshiro stores defaults as strings regardless, which is a known difference, not a bug.

## Consequences

- This amends three earlier ADRs. ADR-0021: the archive carries Field Values on the Plugin, and its note about unrepresented Device-less values no longer applies. ADR-0028: the redacted set swaps secret Plugin Variables for password-type Field Values. ADR-0030: a Recipe Update Check that adds a required field leaves the Plugin, not each Assignment, needing a value.
- The first archive version change that keeps an older version importable. ADR-0021 listed archive schema migrations as a follow-up; this is the narrow first case, not a general migration mechanism.
- Duplicating a Plugin copies its Plugin Fields and Field Values, password-type ones included.
- The per-Plugin `.trmnlp` export carries Plugin Fields, now with select options, and no Field Values, so it stays safe to share.
- Per-Device values are not on the route. Reaching them later means a render and a fetch per Assignment and a rule for Mashup slots, not a column that happens to exist.
- The Webhook-kind Plugin gets Field Values in its templates like any other; it has no Data Source for them to feed.
