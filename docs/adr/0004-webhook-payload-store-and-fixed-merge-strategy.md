# Webhook plugins persist one JSON blob per Plugin; Merge Strategy is fixed per Plugin, not per POST

The Webhook Kind decision (#775) shipped only as documentation — `Plugin Kind` and `Webhook Token` were recorded in the glossary and an ADR was written describing a "render synchronously, discard the payload" v1, but no code was ever merged: no `'Webhook'` value on `Plugin.kind`, no ingest endpoint, no token field. #785 then asked how a Webhook Plugin's data survives across multiple POSTs, so `deep_merge`, `stream`, and GET-to-inspect become possible. Since neither issue had shipped any code, we're building both together rather than shipping the replace-only version first and revisiting later — there's no live behavior to preserve continuity with, so phasing would only mean writing the ingest handler twice.

TRMNL's own webhook plugins take `merge_strategy` as a parameter on every individual POST, letting a caller pick replace/merge/stream per request. We deliberately deviate from that: Merge Strategy is fixed on the Plugin at creation (editable later through the normal edit flow, but never supplied by an individual POST). A per-request strategy means any caller holding the Webhook Token can flip a `stream` Plugin to `standard` on a single POST and wipe its whole accumulated array — a footgun with no compensating benefit for a self-hosted, single-tenant server where the plugin owner and the integration author are the same person deciding the strategy up front.

The persisted payload (the Webhook Payload) is one mutable jsonb blob per Plugin — TRMNL's `merge_variables` equivalent — not a structured or versioned store, since nothing in scope asks for payload history, only current state. `deep_merge` recursively merges objects but replaces arrays wholesale on collision (matching how most deep-merge implementations treat arrays by default, and keeping `stream` as the only strategy that grows arrays). `stream` appends top-level array values with FIFO eviction once length exceeds Stream Limit, and replaces non-array top-level keys normally alongside that. Every POST renders synchronously against the full post-merge blob — not just the incoming body — reusing the same render-and-cache path `PluginSchedulerService` uses for Poll; persisted storage doesn't add a second, schedule-driven render trigger.

`Plugin.kind` moves from an unconstrained `text` column (nothing branches on it today) to a TS union with DTO and DB-level validation, and becomes immutable after creation. Poll and Webhook Plugins now have disjoint required fields (`dataSource` vs `webhookToken`/`mergeStrategy`/`streamLimit`), rejected explicitly at the wrong kind; letting `kind` flip in place would mean every kind-specific code path has to handle stale leftover fields from before the last flip.

`/webhook/:token` (serving both GET and POST, token as the sole lookup key — `Plugin.id` never appears in the URL) is the first place in the codebase to use a NestJS Guard for auth, rather than the inline comparison every other token check uses (e.g. Device API key in `display.service.ts`). Justified here because, unlike those single-method checks, POST and GET on this route share identical auth logic.

## Consequences

- No payload size or rate limits are enforced (TRMNL caps these per subscription tier; Kuroshiro has no tiers to protect) — revisit only if abuse becomes a real problem.
- `GET /webhook/:token` returns the stored blob as-is, no metadata wrapper — Merge Strategy, Stream Limit, and timestamps live in the normal session-authed Plugin admin API instead.
- A separate, session-authed "clear stored data" action exists for debugging a misbehaving integration without deleting and recreating the Plugin.
- `docs/adr/0003-webhook-plugins-render-and-discard.md` is removed rather than marked superseded — it documented a "render and discard" design that was never implemented, so there's no shipped behavior for a superseding record to relate to.
