# Recipe Update Check is manual and three-way against a stored Recipe Snapshot; conflicts are resolved pick-a-side

ADR-0011 made Recipe import a one-time, disconnected copy and rejected auto-propagating Recipe changes because silently overwriting an admin's local edits "needs its own conflict-handling design". Issue #1028 supplies that design: an imported Plugin gains an on-demand **Recipe Update Check** that re-fetches the source Recipe, shows a per-item diff, and applies only what the admin selects. This supersedes ADR-0011's "one-time, disconnected copy" bullet; the rest of ADR-0011 stands. Triage settled the following.

- **Three-way, not two-way, with the import-time copy stored on the Plugin.** A two-way diff (Recipe-now vs Plugin-now) cannot tell "the admin edited this" from "TRMNL changed this". So the importer stores the parsed Recipe it produced as a **Recipe Snapshot** (a `jsonb` copy of the importer's output) on the Plugin, next to the already-stored source Recipe id; `duplicate()` copies it and the Configuration Archive manifest carries it, so a duplicate or a restored instance stays three-way. Plugins imported before the column existed have no snapshot and fall back to a two-way diff, with every item defaulting to keep-local and the UI saying why.
- **Change detection is content hashing, because TRMNL exposes no revision.** We checked: the archive's `settings.yml` has no version or timestamp, the archive's ETag differs on every request (the zip embeds request-time mtimes), there is no `Last-Modified`, and the public `recipes/<id>.json` carries only `published_at`. Terminus does no change detection either. A check therefore always downloads the archive and diffs its parsed content against the snapshot; the hash over the unzipped file contents is what the preview hands to apply so apply can refuse (409) if the Recipe moved in between.
- **Update Items cover everything the importer produces, keyed by natural identity.** Name, description, refresh interval, each template by layout, each Data Source by name (transform included), each field definition by keyname. Diffing only templates and Data Sources, as the issue proposed, would let a template reference a custom field the Plugin never received. Items are `added`, `changed` or `removed` relative to the snapshot; an item is a `conflict` when both the Recipe and the local Plugin moved it. Items that exist only locally are never listed or touched.
- **Conflicts are resolved per item by picking a side.** Alternatives were blocking the item (a customised template could then never take an upstream fix short of re-importing) or an inline merge editor (a tool nobody asked for). Upstream-only changes default to apply; conflicts, including an upstream removal of a locally edited item, default to keep-local, so the safe choice is the default.
- **Apply is whole-item, with one exception.** Applying a Data Source replaces its method, url, body, transform and mode, but keeps local header entries whose keys the Recipe does not set: headers are where admins put credentials, and a Recipe's `polling_headers` change should not wipe them.
- **Local field values and Plugin Assignments are never touched.** A removed field definition takes its stored values with it; a newly added required field leaves assignments missing a value, which the preview reports per assignment rather than blocking apply.
- **Apply always replaces the whole snapshot; dismiss persists nothing.** Applying with nothing selected is a deliberate "treat the current Recipe as my baseline", which also stops kept-local conflicts from reappearing until the Recipe changes again, and is how a legacy two-way Plugin becomes three-way. Closing the preview leaves everything as it was.
- **Per-Plugin and on-demand only.** The action lives on the Plugin; there is no instance-wide check, background polling, badge or notification.

## Consequences

- Apply runs through the same update path as an ordinary Plugin edit, so render-cache invalidation and rescheduling on a changed refresh interval come for free.
- A Recipe that the importer would now reject (deleted, OAuth-enabled) surfaces as an error on the check and changes nothing; the link stays. A `polling`/`static` strategy flip is an ordinary `changed` Data Source item.
- The per-Plugin `.trmnlp` export does not carry the snapshot; a Plugin re-imported through that path loses its Recipe link as it does today.
- Additive follow-ups: an instance-wide "check all", an Alert Rule for available updates, finer-than-item apply.
