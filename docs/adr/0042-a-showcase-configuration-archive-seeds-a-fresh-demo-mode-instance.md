# A showcase Configuration Archive seeds a fresh demo-mode instance

Issue #1384 asks for the public demo — and a contributor's first local run — to show a furnished instance rather than an empty one, the same way the nightly volume wipe leaves the public demo blank today. The triage discussion settled most of the shape; one open question, what exactly triggers this for "local dev start" separately from `KUROSHIRO_DEMO_MODE`, went back to the maintainer. The answer and the rest of the decisions:

- **`KUROSHIRO_DEMO_MODE=true` plus an empty database is the only trigger.** No implicit dev signal. `NODE_ENV` is not consulted — the Dockerfile sets it to `production`, so a contributor's `docker-compose up` and a self-hoster's are indistinguishable by it — and no new environment variable is introduced. A contributor gets the furnished instance by setting `KUROSHIRO_DEMO_MODE=true` in their own `.env`, same as the public demo does. A self-hoster who boots a blank instance without demo mode never sees showcase content.
- **The showcase content is a Configuration Archive, committed to the repo and authored from scratch** — a Device, Screens, a Mashup, a Schedule and Poll Plugins — at the current archive `schemaVersion`, never copied from a live instance. It is written as TypeScript literals (`configuration/showcase/showcase-content.ts`, assembled by `configuration/showcase/showcase-archive.ts`), not a committed `.zip` or a folder of loose JSON/YAML/Liquid files: tsup bundles the API into one file with no asset-copy step, so anything the seed reads at runtime has to be source the bundler already sees. Building the zip in memory from literals needs no new build step and reviews as an ordinary code change, including inline comments explaining each choice — something a plain committed `.zip` can't carry and a committed JSON folder can't either.
- **The import goes through the existing path**, `ConfigurationImportService.importFromZip`, the same one `POST /api/config/import` uses. No second importer.
- **`ShowcaseSeedService`, an `OnApplicationBootstrap` in the configuration module, is the trigger.** It checks `demo_mode` and that both the Device and Plugin tables are empty, then imports. Either condition failing is a quiet no-op (a debug log line, nothing more) — a self-hoster's blank production instance is never touched, and a second boot after the first seed does nothing.
- **It explicitly awaits `DeviceModelSyncService.seedFromSnapshot()` before importing**, rather than relying on bootstrap ordering across modules: Configuration Import only warns and nulls a Device's Device Model/Palette reference it can't resolve (ADR-0021), and `seedFromSnapshot` is already idempotent (it only inserts snapshot rows that don't exist), so calling it again here is harmless and makes the dependency explicit instead of accidental.
- **The showcase Device's `apikey` is the Redaction Sentinel, not a fixed value.** `resolveDeviceApikey` already mints a fresh one for a newly-created Device whose archived value is the sentinel (ADR-0028) — reusing that path means no single apikey value sits in every checkout of this repository.
- **Three Poll Plugins, each a different way of getting data in, per the brief:** an Open-Meteo weather fetch (a real public API, no key), a Countdown with a `literal`-mode Data Source and the day-count computed in Liquid (no network call at all), and a Dad Joke Plugin carrying a `sourceRecipeId` to show a Recipe-imported Plugin in the showcase — a placeholder id (`kuroshiro-showcase-dad-joke`), not a real `trmnl.com` Recipe, so a stray Recipe Update Check fails cleanly ("Recipe not found") instead of silently drifting from a real one. Every fetch-mode Data Source names a public `https://` address; nothing requires a secret.
- **Scheduling needs no extra call.** `ConfigurationImportService` already reschedules every Plugin it upserts (`scheduleUpsertedPlugins`), so the three showcase Plugins start fetching as soon as the import's transaction commits, restart or not.
- **An import failure is logged and swallowed**, not thrown: the instance comes up empty rather than crash-looping on a showcase bug.

## Considered and rejected

- **A committed `.zip` binary, or a folder of loose `manifest.json`/`plugins.json`/… files zipped at boot.** Both need the exact same files to exist on disk wherever the compiled API runs, which means either teaching tsup's single-file bundle to copy non-TypeScript assets, or keeping the archive out of the bundle and reading it by a path relative to the running process — neither of which anything else in this codebase's build does today. TypeScript literals need neither.
- **`NODE_ENV !== 'production'` as (part of) the trigger.** Rejected at triage: the Dockerfile fixes `NODE_ENV=production` for every image, including a contributor's own `docker-compose up`, so it cannot distinguish that from a self-hoster's real deployment.
- **A dedicated seed environment variable.** Would need its own default in `.env.example` and `docker-compose.yml` without accidentally seeding a real self-hoster's blank instance — exactly the ambiguity `KUROSHIRO_DEMO_MODE` already resolves without a second toggle.
- **Scheduling the imported Plugins explicitly from `ShowcaseSeedService`.** Unnecessary: `ConfigurationImportService.scheduleUpsertedPlugins` already does this for every import, manual or seeded.

## Consequences

- A future archive `schemaVersion` bump must update `showcase-content.ts`/`showcase-archive.ts` to match — a test asserts the built archive's `schemaVersion` equals `CONFIG_SCHEMA_VERSION`, so CI fails until it is.
- The showcase Device, its Plugins and their public Data Sources are ordinary rows once imported: an admin can edit or delete them like anything else Configuration Import creates. Nothing is pinned or protected.
- Open-Meteo and icanhazdadjoke.com's public APIs being unreachable only produces a degraded render (ADR-0021's "the rest of the render proceeds with whatever succeeded"), never a failed boot.
