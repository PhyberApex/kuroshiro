# A render page reaches neither the API nor an internal host no admin named

The shared render browser (ADR-0044) was launched with `--disable-web-security`, and Template markup runs in it with JavaScript on. With the same-origin policy off, a script in a Recipe's template, which is third-party code (ADR-0072), could read `http://localhost:3000/api/config/export` (every Device API key and password Field Value in plaintext) on every scheduled render, and a demo visitor posting HTML to `/api/device-preview` could read cloud metadata or a LAN host and get it back drawn into the PNG. The demo-mode guard of ADR-0052 covered Data Source fetches only. Issue #1741.

This decision first scoped the internal-host refusal to demo mode, leaving a self-hosted render page free to reach any private address that was not the API: a router's admin page, a NAS, another container on the same bridge. Issue #1776 asked whether that was the right default, and it is not — the page runs third-party markup on every scheduled render, and nobody installing a Recipe expects it to be able to scan their LAN. So the refusal applies on every Instance, and an admin whose Recipes legitimately render from a local service names what they may reach.

- **Web security is on.** The flag goes. It came in with the first render code and nothing in the repository's history says why. The TRMNL framework's CSS, JS and fonts on trmnl.com answer `Access-Control-Allow-Origin: *`, so they still load.
- **Every render page's requests are checked before they leave the browser.** `withSharedPage` turns on request interception, which leaves the HTTP cache on, so renders still share the framework assets. A refused request fails as a network error would. Each request is checked, a document an `<iframe>` loads too.
- **Refused on every Instance:** anything but `http:`, `https:` and the browser's own `data:`, `blob:` and `about:`; `localhost`, `*.localhost` and any name that resolves to loopback or `0.0.0.0`; the API's port on one of the host's own addresses; the host and port of `KUROSHIRO_API_URL`, which devices use to reach the API and may lead back to it through a proxy; and every internal host the Data Source guard refuses, by name as written and by every address it resolves to.
- **`KUROSHIRO_RENDER_ALLOWED_HOSTS` is what an admin may let back in.** A comma-separated list of host names, address literals and CIDR ranges, empty unless set. An entry that is none of those three is dropped with a logged warning rather than guessed at. `0.0.0.0/0,::/0` is the way to say "the whole network, as before", and says it where an admin can read it back.
- **A host allowed by name carries its addresses with it.** An admin naming `homeassistant.local` cannot also be asked to name whatever it resolves to this week, so the address check is satisfied for that request too. An allowed range, in contrast, is checked against the addresses themselves, so a public name resolving into it is reaching an address its admin already allowed.
- **Refused in demo mode as well:** any name that does not resolve, since then no address of it was checked. The allowlist is ignored there: a public Instance has no network of its own to reach.
- **In demo mode the guarded fetch makes the request.** A request the check lets through is made by `fetchPublic` and the page is answered with its response, so Chromium never connects itself. `fetchPublic` checks the address it connects to and each redirect. A name that answers a public address to the check and a private one to the connection (DNS rebinding) is refused, as it is for a Data Source.
- **No window opens.** Chromium's popup blocker stays on (Puppeteer turns it off by default). A window a script opens would be a page of its own, and no guard would watch its requests.

## Considered and rejected

- **Refusing private addresses on a self-hosted Instance too.** A self-hosted Recipe may read a Home Assistant or another service on the LAN from client-side JS. The admin chose to run it and owns that network. The API, which holds the secrets, is refused. _(Reversed above: owning the network is a reason to be asked which of it to open, not a reason to open all of it. Naming the one service is a line of configuration; a Recipe reading the rest of the LAN is not something the admin chose.)_
- **A boolean that turns the guard off.** It is the setting people paste into a compose file and forget, and it reads as "allow the LAN" while meaning "allow every private range there is", cloud metadata included. A list makes an admin say which host they meant, and leaves the rest refused.
- **Refusing the allowlist from reaching the API.** It cannot: loopback, the API's port on the host's own addresses and `KUROSHIRO_API_URL` are checked before the allowlist is consulted, so naming them changes nothing. An admin who allows the API's own Docker network still cannot read `/api/config/export` through a render page.
- **Flipping the default only for fresh installs.** There is nowhere to keep "this Instance predates the change" that an admin would not also have to understand, and the installs that most need the guard are the oldest ones.
- **Answering every request through `fetchPublic` on a self-hosted Instance too.** It would bypass the shared HTTP cache for the framework assets (ADR-0044) on every render. Outside demo mode, the threat is the API, and loopback is refused by name and by address.

## Consequences

- Client-side JS in a template that reads another origin needs that origin to answer CORS, as it would in any browser. A Recipe relying on the old flag to read an API without CORS headers now gets a network error; its transform or Data Source can fetch the data instead.
- Outside demo mode the check resolves a name, then Chromium resolves it again to connect. A name that answers a public address to the check and loopback to Chromium could still reach the API. Only someone who controls that name's DNS can do it, from a Recipe the admin imported.
- In demo mode the framework assets are fetched on every render, as a fulfilled response is not cached.
- The API is refused at the addresses it can be known by: loopback, its port on the host's own addresses, and `KUROSHIRO_API_URL`. If the API is published on a Docker host's gateway or LAN address under another port, or behind a proxy under another name, it can still be reached there on a self-hosted Instance.
- A Recipe pointing a render page at a LAN service stops working on upgrade until its host is named in `KUROSHIRO_RENDER_ALLOWED_HOSTS`. A Home Assistant add-on install is the likely case, and the add-on, which lives in its own repository, has to pass the variable through for it. The failure looks like a network error in the template, as a refused request always has.
- An allowlist entry is matched as written, with no resolution of its own: a name is compared to the name the page asked for, so allowing `homeassistant.local` does not allow another name answering the same address.
- WebSocket connections bypass request interception. The API serves none.
