# Colour panel PNGs stay minimally-indexed; a saturation boost precedes the remap

`paletteOperators()` in `packages/api/src/utils/imageUtils.ts` produces indexed PNGs (`color-type=3`) whose `PLTE` only contains the colours actually used by a given image, rather than the palette's full colour set in a fixed order. Whether TRMNL colour firmware needed a fixed palette order/depth was unverified (#756).

Checked `usetrmnl/firmware` (`src/display.cpp`) for the two boards with a dedicated colour draw callback: `BOARD_TRMNL_4CLR` (`color-4bwry`) and `BOARD_SEEED_RETERMINAL_E1002` (`color-6a`). Their callbacks (`png_draw_4clr`, `png_draw_6clr`) read the real `PLTE` RGB triplet for each pixel's index (`pPalette[s[0] * 3]`, etc.) and pass it through `GetBWYRPixel`/`GetSpectraPixel`, which classify the RGB value against the panel's fixed hardware colours by threshold/nearest-match — they never assume an index position maps to a specific colour, and they accept any of the standard indexed bit depths (1/2/4/8) ImageMagick's `-remap` may choose. **For these two palettes, no format forcing is needed**; a minimal, arbitrarily-ordered `PLTE` is already correct.

The generic `png_draw()` path — used for every other board, including the waveshare BWR/BWRY panels behind `color-3bwr` and whatever backs `color-7a` — has no equivalent RGB-matching code in this repo: `GetBWRPixel` (the 3-colour analogue of `GetBWYRPixel`) is defined but never called, and `BBEP_7COLOR` is only referenced for a wait-time check. Multi-colour PNGs there fall into `ReduceBpp`'s luminance-threshold plane-splitting (`(pPal[0] + pPal[1]*2 + pPal[2])/4`), which has no chromatic (red/yellow) matching at all. Whether those boards get their colour from the closed-source `bb_epaper` library (a PlatformIO dependency, `bitbank2/bb_epaper@2.1.9`, not vendored in this repo) reinterpreting the plane bytes, or don't yet support colour PNGs on this firmware snapshot, could not be determined from `usetrmnl/firmware` alone. **`color-3bwr` and `color-7a` remain unverified** — acceptance criterion 1 is met only for `color-4bwry` and `color-6a`.

The 4CLR/E1002 firmware code also explains why colour rendering benefited from Terminus's (`usetrmnl/terminus`, `app/aspects/screens/converters/color.rb`) `-normalize -modulate 110,150 -colorspace RGB … -remap … -colorspace sRGB` pipeline: `GetBWYRPixel`'s thresholds (e.g. red requires `r-b > 32 && r-g > r/2`) reject under-saturated source colours as white/gray. We adopted the same boost, applied before `-remap` and reverted to sRGB afterwards so the following `-remap`/dither step operates on the intended colour space, in `paletteOperators`'s `'color'` case. It's applied uniformly to all colour palettes rather than gated by board — it's a source-image enhancement independent of which on-device matching strategy consumes it, and Terminus applies it the same way regardless of target panel.

## Consequences

- All colour palettes (`color-3bwr`, `color-4bwry`, `color-6a`, `color-7a`) get a systematic saturation lift before dithering; grayscale and full-colour palettes are unaffected.
- No hardware test was performed for any palette; `color-4bwry` and `color-6a` have source-level confirmation instead. `color-3bwr` and `color-7a` have neither — a real waveshare BWR/BWRY or 7-colour device (or the `bb_epaper` library source) still needs to confirm the produced PNG is accepted before we can close out the equivalent question for those two.
