# Configuration Archive v1: secrets in plaintext behind a warning, exported ids as identity, restore targets a fresh instance

Issue #977 asks for a whole-server Configuration Export/Import so an admin can back up, diff, and move everything they built in Kuroshiro without a raw `pg_dump`. The only existing surface is the per-Plugin `.trmnlp` export (`PluginExporterService.exportToZip`) and its create-only importer. Triage settled five decisions the issue left open:

- **Secrets are exported as-is, not redacted.** Data Source headers (bearer tokens etc.) and Device `apikey`/`mirrorApikey` go into the archive verbatim. The export UI and the API response carry an explicit warning that the archive contains credentials and must be stored accordingly. A redact-and-prompt-on-import flow would double the import surface (placeholder resolution, partial restores) for a self-hosted tool whose admin already holds the DB; the per-Plugin exporter has always written headers verbatim, so this keeps the two exports consistent. A redacting mode can be added later as an opt-in without changing the archive shape.
- **Exported `id`s are the identity key.** Every record keeps its UUID in the archive, and import upserts on that id. `Plugin.name` is not unique (#969) and inventing a slug per entity would be a schema change across seven tables for no gain — the UUIDs already exist and are stable across export/import cycles.
- **v1 restore targets a fresh instance.** Import is an upsert by id, so re-importing the same archive is idempotent, but merging onto an instance that already holds unrelated content (Order collisions on a Device, a Palette the archive doesn't know about) is deliberately not designed here. Merge semantics onto a populated instance are a follow-up.
- **Devices re-attach by `mac`.** `mac` is unique and is what physical hardware identifies itself by. A Device in the archive whose `mac` matches an existing row updates that row (keeping the exported `apikey` so the hardware keeps working). A Device whose `mac` matches nothing is created as-is; the archive's Screens and assignments attach to it, so a restore onto different hardware still reproduces the configuration and the admin re-pairs by editing the `mac`. User-driven remapping at import time is a follow-up.
- **The archive nests the existing `.trmnlp` layout per Plugin.** Each Plugin lives at `plugins/<id>/` in exactly the shape `exportToZip` already produces, so a single folder zipped on its own is still importable through the existing per-Plugin path (consistent with ADR-0010's "one importer, adapters in front" stance). Everything that has no `.trmnlp` equivalent — Plugin id/kind/Webhook fields, Devices, Screens, Schedules, Mashups, assignments and their field values, custom Palettes, custom Firmware metadata — lives in top-level manifests.
- **Version stamp; refuse on mismatch.** The archive carries the Kuroshiro version and a `schemaVersion` integer owned by the archive format. Import refuses an archive whose `schemaVersion` differs from the running instance's, with a message naming both. No migration of old archives in v1.

## Consequences

- The `.trmnlp` shape inside the archive is now a contract two exporters share; changing it means changing both (or, better, having the whole-server exporter call the per-Plugin one).
- Runtime state — Webhook Payloads, Sensor snapshots, rendered image caches for `plugin`/`mashup`-type Screens, logs, `lastSeen`/battery/RSSI, official-synced Palettes and Firmware — is not in the archive. A restore reproduces configuration, not history. The one exception is a `file`-type Screen's converted PNG (`public/screens/devices/<deviceId>/<screenId>.png`): for that Screen type it is the only persisted admin-supplied content, not a regenerable cache, so the archive keeps it. The pre-conversion original upload is not retained either way, so a restored `file`-type Screen that's later reconverted for a different Device Model (`ScreensService.reconvertImageScreens`) reconverts from that once-converted PNG rather than a pristine source.
- Custom Firmware binaries are not in the archive, only their metadata; a restored `custom` Firmware row without its file cannot be served until re-uploaded.
- `PluginFieldValue` rows with no `Device` (a plugin-wide default rather than a per-Device override) are not represented anywhere in the archive: `ConfigurationExportService.buildAssignmentEntry` only ever emits field values scoped to a Device+Plugin pair. Nothing in the running app creates a Device-less value today, so this isn't reachable in practice, but closing it later means adding a place for plugin-scoped values in the manifest, not just relaxing the filter.
- "Every record keeps its id, which is the identity Configuration Import upserts on" has one carve-out: a Plugin's Data Sources, Templates and Fields live inside the shared `.trmnlp` `settings.yml`/`fields.yml`, which carries no id field of its own, so `ConfigurationImportService.upsertPluginDataSources`/`upsertPluginTemplates`/`upsertPluginFields` recover the archived id by matching the re-parsed entry's `name`/`layout`/`keyname` against the manifest's id list, minting a fresh `randomUUID()` on a miss. Re-importing an unmodified archive matches every time, so idempotency holds; a Data Source, Template or Field renamed on the target instance between two imports of the same archive won't be matched by the new import, so it's created anew alongside the stale original rather than updated in place. Closing this means giving `.trmnlp` an id field, which is a breaking change to the format the per-Plugin exporter/importer also uses.
- Follow-ups that stay additive: opt-in secret redaction, merge-onto-populated-instance semantics, Device remap UI at import time, archive schema migrations, retaining a `file`-type Screen's pre-conversion original, exporting/restoring Device-less Plugin field-value defaults, an id field in `.trmnlp` for Data Sources/Templates/Fields.
